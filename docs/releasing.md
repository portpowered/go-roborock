# Releasing

Choose the SDK and CLI version before verification (for example, `v0.2.0`). Update the CLI's SDK requirement and the version-specific workspace replacement, and verify local module metadata before tagging. Every version below means that selected version; existing published tags are immutable.

1. Have two independent reviewers inspect the implementation against `docs/standards/` and the template library standards. Resolve code findings and record the reviewed SHA. Keep external release-evidence items open until published module tags and consumer installations can be verified.
2. Run `make lint` and `make check`. Confirm generation, schema/source contracts, module tidiness, builds, race tests, replay, CLI, and at least 80% combined non-generated production coverage.
3. Build all schemas and customer guides with the pinned shared Fumadocs action. Run `go run ./tools/sitelinks -root site -base /go-roborock`. Inspect guide content, generated reference navigation, root links, and external release-note URLs. Confirm separate unit/replay/combined reports.
4. Merge to main and wait for both CI and Documentation to succeed on that exact commit. GitHub Pages must use the GitHub Actions publishing source. Open the published guides and reports and confirm their expected content.
5. Tag the SDK's selected version at the verified implementation commit. Wait for tag verification and the workflow's draft GitHub release. The tag makes the Go module downloadable; the draft remains unpublished while final release evidence is collected.
6. Run `GOWORK=off go mod tidy` inside `cmd/go-roborock` against the tagged SDK to record its real checksum. Commit only the nested module metadata changes. Independently review this metadata commit, verify the root implementation tree is identical to the SDK tag and only CLI `go.mod`/`go.sum` changed, and rerun CLI verification. Tag the corresponding CLI version, such as `cmd/go-roborock/v0.2.0`, at that verified metadata commit and wait for its workflow, including the clean consumer installation.
7. From a clean consumer module, install the tagged SDK and CLI. Confirm module resolution, CLI help, and public examples. Verify the Go Reference, CI, coverage, and Pages destinations. Have both independent reviewers confirm all 16 checklist items, exact SDK and CLI commits, passing CI, and the external release evidence in the current review record.
8. Publish the SDK's draft GitHub release only after the final reviews pass. Review release notes for supported scope, evidence status, known exclusions, and working published guide links. Confirm the public release page and README release badge resolve correctly.

Never release a different commit on the strength of an earlier CI run. A module tag or draft release alone does not complete publication. Keep [the checklist](checklist.md) and [independent review record](review.md) tied to the exact verified commits and evidence.
